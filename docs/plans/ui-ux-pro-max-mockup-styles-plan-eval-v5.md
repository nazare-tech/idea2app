BLOCKER verification "Risk-Matched Verification" / Phase 3 flag default — the feature ships default-on to every new generation while the only evidence for the primary risk (does the OpenRouter image model actually honor a restructured treatment block?) is explicitly absent, and no production quality signal is defined to catch it. If adherence degrades, every paid mockup after deploy is worse and nobody learns until users complain. Fix: ship `MOCKUP_PROMAX_ENABLED` default off, gate default-on behind either an approved single real-provider sample or an internal-account rollout, and define the counter that would trigger flag-off.

BLOCKER product "Runtime and Change-Impact Analysis → Repeated Work" / "Retry changes style" row — the plan makes persisted A/B/C IDs win over recomputation for *all* retries, without separating crash/recovery retry from a user-initiated "regenerate this option". A founder who dislikes option B pays credits to regenerate and provably receives the same visual system every time, with no picker (deferred) and no escape. Fix: key stability to run-recovery only; user-initiated regeneration must reselect (next-ranked candidate in the same role) and rewrite the persisted ID for that slot.

BLOCKER security/data-integrity "Boundary And Cache Semantics" / "Catalog freshness" — persisting only `source + catalogVersion + treatmentIDs` assumes every ID survives future offline regenerations of the lookup, but the generator's allowlists and rejected-set can drop an ID. A retry after a catalog refresh then cannot resolve a persisted ID and falls back to the legacy bank for one option inside a Pro Max triad — the exact mixed-triad state the plan forbids, on a paid path. Fix: persist the resolved, capped treatment payload (or maintain an append-only never-delete ID registry with tombstoned retired entries) so old runs reconstruct without the current lookup.

MAJOR runtime "Failure And Recovery → Kill switches" vs "Retry changes style" — two rules contradict for a run that persisted Pro Max IDs and is retried after `MOCKUP_PROMAX_ENABLED=0` is deployed: "persisted IDs win over recomputation" says Pro Max, "flag 0 selects the current bank" says legacy. As written, whichever branch is coded first produces either a mixed triad or an unrenderable treatment lookup after rollback. Fix: state explicitly that flag=0 forces whole-run legacy including recovery of Pro Max runs (accepting one visual discontinuity), or that persisted selections are honored regardless of flag and the flag only affects *new* selections — and test that case.

MAJOR runtime "Rollback And Recovery" — a code revert leaves `styleSelection` inside saved `mockup_option_drafts.design_plan` and `mockups.metadata.design_plan`, and the plan never checks whether the existing design-plan parser tolerates unknown keys. If that parser is strict, post-revert recovery of in-flight runs fails to parse and strands partially generated, already-charged options. Fix: confirm the parse mode in the `MockupDesignPlan` parser (`src/lib/prompts/mockups.ts` or `src/lib/mockups/*`) before Phase 3, and add a test that a plan containing `styleSelection` parses under the pre-change parser.

MAJOR runtime "Runtime selector" input contract — "design plan and primary platform" assumes a platform field already exists on `MockupDesignPlan`; if it does not, this is an unacknowledged planner-prompt/schema change that alters the LLM output contract and every existing saved plan lacks it. Selection would silently default to one platform and mobile products get web-density treatments. Fix: name the source field explicitly (I would need `src/lib/prompts/mockups.ts` and the `MockupDesignPlan` type to confirm it exists); if absent, add a Phase 2 step for deriving platform from existing plan fields with a tested default.

MAJOR verification "Selector silently falls back" row / "Legacy-bank removal criterion" — the plan promises a counted `mockup_promax_fallback` diagnostic and a "<1% for two releases" gate but never says where that count is stored; `product_events` is an allowlist-gated, service-role-only, content-free table whose contract file is not touched by any phase. As written the event is either dropped by the allowlist or is a console log that cannot be aggregated, so the removal gate and the rollback trigger are both unmeasurable. Fix: add a Phase 3 step registering the event/property in `src/lib/product-analytics/contracts.ts` (IDs only), or state plainly that the gate is manual log inspection and drop the percentage threshold.

MAJOR security "Prompt integration" — the plan describes rendering treatment fields as "structured key/value lines" appended at the `generateAndStoreOption()` seam without routing through the documented `buildSecurePrompt()` / `sanitizeInput()` / `<user_input>` delimiter path that repo convention requires for all prompt assembly. A second, hand-rolled prompt-assembly path in the same file diverges the moment the sanitizer is hardened, and the "no instruction-shaped text" denylist becomes the only defense for catalog-derived strings. Fix: assemble the treatment block through the existing secure prompt builder as a trusted-block API, and add one test asserting the mockup prompt has no direct string concatenation of catalog fields.

MAJOR verification "Visual provider ignores guidance" row — "three treatments visibly differ" via built-in image generation has no judging procedure, no pass/fail rubric, and no artifact retention rule, so it cannot fail; meanwhile the automated triad test only asserts distinct *IDs* and "two distinct surface/type treatments", which three near-identical minimal-SaaS styles can satisfy. Built as planned, the collapse risk the table claims to cover is unmitigated. Fix: define the distinctness assertion on concrete generated fields (palette hue distance, type family, density, surface treatment must each differ across at least two pairs) and treat the image sample as informational only.

MAJOR verification "Product misclassification" row / Phase 2 "Freeze accepted/rejected upstream results before implementation" — the accepted/rejected mapping, the ten-idea fixtures, and the selector are all authored by the same implementer, so a wrong product-category mapping produces green tests. The stated "cannot self-bless" threshold is not enforced by anything. Fix: derive the expected product category for the ten ideas from an independent source (the upstream `products.csv` `Best For` column matched by hand and recorded with row citations) and require the fixture to name the upstream row that justifies each acceptance.

MAJOR product/scope "Implementation Phases" vs `docs/operating-system/ui-verification.md` — Phase 4 plans fixture-mode workspace evidence as the browser regression, but the repo's verification policy forbids fixtures/stubs for user-visible changes and requires reporting a blocker instead. The plan quietly substitutes a prohibited evidence class rather than surfacing that this change cannot be verified under the current constraints. Fix: state the conflict as an open decision for the user (approve one real generation for evidence, or accept shipping with no real-flow evidence and default the flag off).

MINOR architecture "Runtime selector" — "stable content hashing only for exact ties" leaves the hash input unspecified; if it hashes design-plan prose, a one-word planner variation flips the tie and the "deterministic" claim holds only for byte-identical plans, which is not what the determinism test will exercise. Fix: hash a stable, explicitly listed key (project id + role letter + candidate ID set), not free text, and assert it in the determinism test.

MINOR architecture "Source snapshot" / Phase 1 — vendoring 0.4–1.8 MB of CSVs plus frozen raw fixtures plus a generator script to produce a sub-100 KB lookup means three artifacts must stay in sync, and only the manual regeneration procedure keeps them honest; drift between committed fixtures and committed lookup is invisible after the first update. Fix: add a CI check that re-runs the generator from the pinned CSVs and diffs against the committed lookup, or drop the frozen raw fixtures and keep only CSVs + generator + lookup.

MINOR security "Source snapshot → License gate result" — the gate is recorded as already passed ([x]) on the basis that no separate data exception was *found*, which does not establish that the catalog rows are the upstream author's to relicense. Fix: record in the provenance note that only the upstream declaration was checked, and restrict the vendored payload to the columns the generator actually reads.

MINOR runtime "Ownership, Scope, And Lifetime" — the enriched design plan is stored in client state/localStorage for the manual A/B/C path, and the plan asserts the client payload envelope is "unchanged" while adding three treatments' worth of guidance, palette, typography, effects, and anti-pattern fields to it.
