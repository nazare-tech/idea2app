MAJOR runtime-and-change-impact "Implementation Phases" / "Repeated Work" — the plan describes "one ownership-scoped mockup query for visible project IDs" ordered `created_at DESC, id DESC` but no `limit`, no column projection, and no per-project deduplication in SQL; PostgREST cannot express "latest row per project" without DISTINCT ON in an RPC or view. Built as written, a user who has regenerated mockups pulls every historical `mockups.content` JSON for every project on every `/projects` render and discards all but one row per project, so dashboard latency and payload grow with regeneration history rather than project count. Fix: select only `id, project_id, created_at, content`, add a bounded `limit`, and either add a `DISTINCT ON (project_id)` view/RPC or document the JS-side newest-row reduction with an explicit row cap.

MAJOR runtime-and-change-impact "Failure And Recovery" / "Test Strategy" — the plan never states the size of the asset behind `/api/mockups/image`; Version A is a full-resolution generated mockup, and every card renders it through an authenticated serverless proxy that must auth-check and stream the object. A 12-project dashboard fires 12 concurrent function invocations and downloads full-size images to paint ~300px thumbnails, which is the actual cost the "Deferred — dedicated dashboard thumbnail column or derivative image" option was dismissed as disproportionate against. Fix: either request a Storage image transform (width/quality) through the proxy as a query param, or batch `createSignedUrls` so the browser fetches from Storage/CDN directly instead of N function invocations.

MAJOR runtime-and-change-impact "Failure And Recovery" / Cross-Model section — "Dashboard freshness follows normal server navigation/refresh behavior. No new cache introduced" ignores the Next.js App Router client-side Router Cache: after Generate All completes mockups, a client-side navigation back to `/projects` can serve a cached RSC payload rendered before the mockup existed, so the card shows the empty state with no user-visible way to distinguish it from "never generated". Fix: call `router.refresh()` on mockup-queue completion in `generate-all-store.ts`, or set the dashboard route to explicitly opt out of the router cache and say so in the plan.

MAJOR premises "Test Strategy" (newest-row selection) — "malformed/retired newest row does not fall through to older content" assumes the newest `mockups` row is always the best row, but the plan never checks a status/completion field; if a Generate All run inserts a mockup row before/while image options are persisted, or a run fails and persists a partial payload, a project that previously showed a thumbnail silently goes blank. Fix: select the newest row whose canonical parse yields a usable Version A `storagePath` (filter, then take newest), and state explicitly whether `mockups` has a status column — I would need `src/lib/mockups/openrouter-image-format.ts` and the mockups insert path in `/api/mockups/generate` to confirm the persisted shape mid-run.

MAJOR verification "Test Strategy" (Node component rendering tests) — tests run under Node's built-in runner via tsx with no DOM, so a component test can only assert server-rendered output; the claimed coverage that "component load error swaps the media region back to the empty state" cannot execute, because `onError` never fires and the fallback `useState` never transitions in a string render. Built as planned, the error-fallback path ships with zero automated coverage while the plan records it as tested. Fix: extract the fallback decision into the pure helper (or a tiny reducer) and unit-test that, and downgrade the DOM-dependent assertion to real-Chrome evidence explicitly.

MAJOR security "Runtime and Change-Impact Analysis" / Ownership — the plan asserts "Existing user-owned `mockups` rows" and an "ownership-scoped" query, but never names the scoping mechanism: `mockups` is described in the schema doc as project-scoped via the owning project, so correctness depends on the page using the RLS-bound server client and filtering to project IDs already authorized for the session. No test in the strategy would fail if the query used a service-role client or an unfiltered `.in('project_id', …)` built from an untrusted list. Fix: state that the query uses `createClient` from `@/lib/supabase/server` with the caller's session, derive the ID list from the already-authorized projects result, and add one test asserting the derived thumbnail map contains no entry for a project not in that list — I would need `src/app/projects/page.tsx` to confirm which client it currently uses.

MAJOR premises "Boundary And Cache Semantics" — the whole data path rests on `buildMockupImageProxyUrl({ projectId, storagePath })` existing with that signature and on the canonical parser exposing a normalized `storagePath` per option; the plan treats both as given and lists "reuse only" with no verification step. If the proxy actually keys on mockup row id rather than `(projectId, storagePath)`, the entire derivation phase is wrong and Phase 3 blocks. Fix: make Phase 1 verify the helper signature and the parser's normalized option shape against `src/lib/mockups/openrouter-image-format.ts` and the `/api/mockups/image` route handler before writing derivation tests.

MINOR product "Assumptions" / empty-state copy — "Mockup preview will appear here" is shown to three different populations, including retired-HTML-mockup projects where a preview will in fact never appear and projects that have never started generation; the copy states a future that is false for the first group and gives no next action for the second. Fix: use copy that is true for all three (e.g. "No mockup preview") and, for projects with zero mockups, make the slot a quiet affordance into the mockups section rather than dead space.

MINOR product "Goal" / scope — the stated goal is "Show generated mockup Version A when a canonical image mockup exists", but the selected Recommendation A plus strict newest-row-only selection means a project whose newest row is retired HTML while an older canonical row exists renders empty; that combination is a silent scope reduction beyond "Version A only" and is never surfaced as a decision.
