MAJOR verification "Test Strategy" / "Card-level source-contract tests" — asserting that the component contains `min-h-[26.875rem]`/`min-h-[11.75rem]` class strings tests only that the string equals itself; it cannot fail for any of the ways this change actually breaks (parent grid `items-stretch` equalizing rows, an ancestor `overflow-hidden`, Tailwind purging an arbitrary value, a competing `h-full`). Every listed geometry risk would still pass CI and only surface in manual Chrome inspection, which is the step most likely to be skipped on a follow-up edit. Fix: replace class-string assertions with rendered-DOM assertions on the element that owns the constraint, and treat the browser bounding-box measurement as the sole geometry gate — don't claim test coverage for height.

MAJOR premises "Risk-Matched Verification" table vs. "Ownership, Scope, And Lifetime" — the design uses `min-height` (430px/188px) but the acceptance threshold is "card is 430px ±2px and lower panel is 188px ±2px", which are mutually exclusive the moment a description hits four lines or a title wraps; the verifier has no rule for whether a 452px card is a pass or a fail. Whoever implements this will either force a fixed height (clipping content) or declare any measurement a pass. Fix: state the contract as "430px when content is at or below the clamp; grows only via the description panel" and give the table two rows: short-content card measures 430±2, max-content card measures 430 or greater with no clipping.

MAJOR product "Failure And Recovery" / "explicit four-line clamp" — descriptions longer than four lines become permanently unreachable on `/projects`: the plan adds a `title` tooltip for the name but not the description, and the acceptance threshold simultaneously demands "no overflow or unreachable content". Users lose context they wrote, with no affordance indicating truncation. Fix: either add the same full-text `title` on the description element or accept truncation explicitly and drop the "no unreachable content" criterion; decide before implementation, not during browser verification.

MAJOR runtime "Plan" step 3 — the plan audits only the loading skeleton, but `/projects` almost certainly also renders a zero-projects empty state and/or a "new project" tile in the same grid (project-allowance gating is a documented dashboard feature). MAJOR runtime "Clarifying Questions" Q2 / "positioned over the preview" — moving the delete control into an absolute overlay above the padded preview requires a positioning context and a stacking order above the full-bleed `<Link>`; the plan states the delete trigger is a sibling of the link but never specifies which element is `relative`, which gets `z-index`, or that the link must not cover the button. If the link overlay wins the stacking order, delete becomes silently unclickable — a paid-plan feature broken with no test that would catch it (the planned test only asserts the trigger is outside the link, which stays true). Fix: specify the positioning/z-index contract in the plan and add a rendered-DOM or real-Chrome click assertion that the delete trigger receives the click, not the link.

MAJOR architecture "Ownership, Scope, And Lifetime" — mixing rem-relative container heights (26.875rem/11.75rem) with a pixel media cap (216px) means the two halves diverge under a user root-font-size change: the card and panel grow, the image does not, so the preview frame gains dead space and the 430 = preview + panel relationship the plan calls a "contract" stops holding. The planned 200% *browser zoom* check scales px and rem identically and therefore cannot detect this. Fix: express the media cap in rem as well (13.5rem), and change the accessibility check to a 24px root font-size test rather than browser zoom.

MAJOR product "Assumptions" / Q1 Recommendation A — keeping the responsive grid while hard-coding Figma's internal geometry leaves wide-column behavior undefined: at a 560px+ grid column the 216px-capped, centered image sits in a large empty frame above a fixed 188px panel, which is not what node `435:5578` shows and is not covered by any acceptance row (only "desktop and narrow"). The result ships as a card that looks correct only near 420px. Fix: decide now whether the preview frame scales with card width (aspect-ratio box) or the card gets a `max-width`, and add a wide-column row to the verification table.
