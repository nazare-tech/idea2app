BLOCKER security-and-data-integrity docs/plans/…-plan.md "Boundary And Cache Semantics" / Phase 3 — the plan never states how `thumbnailUrl` is constructed from the parsed content: raw storage URL, signed URL persisted in the payload, or a `/api/mockups/image` proxy URL. It asserts the proxy "remains the browser image boundary" without a step that builds proxy URLs. If built as written, the card can emit a bucket URL directly (bypassing ownership validation, or 403ing on a private bucket) or emit an expired signed URL and show broken images on every older project. Fix: add an explicit derivation step that maps the parsed Version A reference to the existing `/api/mockups/image` proxy URL form, and name the field/shape it reads; requires reading `src/lib/mockups/openrouter-image-format.ts` and `src/app/api/mockups/image/route.ts` to confirm.

BLOCKER runtime-and-change-impact "Architecture Improvement Opportunities #2" ("payloads are small") — mockup `content` for `openrouter-image-v2` may embed base64 image data or full multi-option payloads; the plan asserts smallness without evidence and selects the whole `content` column for every project on the dashboard. If images are inline, a 20-project dashboard transfers tens of MB per render and the page times out. Fix: verify payload shape in `src/lib/mockups/openrouter-image-format.ts` and the generate route before choosing this design; if content is large, select a narrowed projection or add the deferred derivative field now rather than after a production regression.

BLOCKER verification-and-rollback "Test Strategy" / risk matrix row "Wrong option shown" — both unit tests target the presentational component, which receives `thumbnailUrl` as a prop; the actual Version-A selection (parse content, match label `A`, build URL, pick among multiple mockup rows) is untested. A selector that returns option B, the newest row, or the first array element passes every listed test. Fix: extract the derivation into a pure exported function (e.g. `selectVersionAThumbnail(content)`) and put the A-vs-B, malformed, retired-HTML, and multi-row cases there; keep component tests for rendering only.

MAJOR premises "Runtime and Change-Impact Analysis" — the plan assumes one mockup row per project ("linear row-to-project lookup") but `mockups` is a project-scoped table with PATCH `/api/mockups/[id]` and regeneration; nothing specifies ordering or tie-breaking. With two rows, the thumbnail becomes whichever row the database returns first and can change between refreshes. Fix: define the winning row explicitly (e.g. latest `created_at`/`updated_at` per project, with a deterministic tiebreak) and cover it in the derivation test.

MAJOR runtime-and-change-impact "Boundary And Cache Semantics" ("no new cache introduced") — Next.js App Router client-side router cache means navigating from the workspace back to `/projects` after generating mockups serves the cached RSC payload; the new thumbnail will not appear until a hard refresh. The plan treats this as normal freshness and adds no invalidation. Users will report "my mockup isn't showing." Fix: add `revalidatePath('/projects')` (or equivalent) on mockup generation/PATCH completion, or document and verify the exact staleness window as part of real-UI evidence.

MAJOR product-and-scope "Failure And Recovery" / Critique ("Do not imply that generation is running") — a project whose mockups are currently generating or queued (`generation_queue_items`) renders the identical empty state as a project that has never generated, and the server-only render never updates. The dashboard actively misinforms during the longest generation step (mockups run ~790s). Fix: either read queue state for a distinct in-progress affordance, or state explicitly that in-progress projects show the plain empty state and confirm that copy does not read as "no mockups exist."

MAJOR verification-and-rollback "Test Strategy" real-Chrome step ("when existing account data supports both") — combined with the assumption that retired HTML mockups yield no image, the generated-thumbnail state may be unverifiable on the test account, and `ui-verification.md` makes fresh generation opt-in and paid. As written the feature can ship with only the empty state ever observed in a browser. Fix: before implementation, confirm the test account has at least one `openrouter-image-v2` mockup row; if not, ask the user to authorize one generation or supply a seeded project, and treat that as a prerequisite, not a nice-to-have.

MAJOR runtime-and-change-impact "Repeated Work" — the plan counts server work but not client work: every card issues a full-resolution mockup image request through an auth proxy that revalidates ownership per request and likely sets no cache headers. A 20-project dashboard fires 20 uncached full-size image downloads on load. Fix: add `loading="lazy"`, explicit width/height or aspect-ratio to prevent layout shift, constrained rendered size, and check/add cache headers on the image proxy response.

MAJOR architecture-and-reuse "Test Strategy" (unit test asserts "no `<img>`") plus Phase 5 "targeted lint" — the plan implies a raw `<img>`, which `eslint-config-next` flags via `@next/next/no-img-element`; using `next/image` instead requires `remotePatterns`/loader configuration that the plan never mentions and will throw at runtime for an unconfigured host. Either path fails a listed acceptance gate. Fix: decide `next/image` vs `<img>` in the plan, and if `next/image`, add the `next.config` host configuration (or a proxy-relative path) as an explicit step.

MINOR runtime-and-change-impact "Failure And Recovery" — relying on "native image behavior" for a failed load puts a broken-image glyph in the dashboard grid, which is worse than the deliberate empty state the plan designed. Fix: give the thumbnail component an `onError` handler that swaps to the empty state (the card is already a client component, so this costs nothing).

MINOR product-and-scope "Test Strategy" ("project-specific alt text") — the thumbnail sits inside a card that already exposes the project name as its link text, so descriptive alt text makes screen readers announce the name twice per card. Fix: render the image with empty alt (decorative) and keep the accessible name on the card link; keep meaningful alt only on the empty state.
