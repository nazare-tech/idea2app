MAJOR product-and-scope — Plan §"Assumptions" (desktop first slide shows Next only … last shows Previous only) — arrows are conditionally rendered rather than disabled, so pressing Next into the last slide unmounts the focused button and drops focus to `<body>`. A keyboard user is dumped out of the grid mid-card on every traversal to an end slide, and the stated "keyboard users can use the labeled arrow controls" fallback fails exactly at the boundaries. Fix: always render both arrows with `disabled`/`aria-disabled` at the ends, or move focus to the opposite arrow before hiding; add a Playwright assertion that `document.activeElement` remains inside the card after reaching each end.

MAJOR product-and-scope — Plan §"Assumptions" / §"Architecture Improvement Opportunities" (dots as sibling buttons, one semantic arrow set) — the plan adds up to 5 extra focusable controls per card with no tab-order strategy. On a dashboard of 10 projects that is ~60 additional tab stops before any content below the grid, a concrete keyboard regression on a page that today has one link plus a menu per card. Fix: specify a roving-tabindex/tablist pattern (single tab stop per card's control group, arrow keys to move between dots) and assert tab-stop count per card in the Playwright keyboard test.

MAJOR runtime-and-change-impact — Plan §"Architecture Improvement Opportunities" (capability-driven CSS via `(hover: none) and (pointer: coarse)`) — the plan dismisses hybrid devices as "unusual", but touchscreen Windows laptops report `pointer: coarse` as primary while being driven by a mouse. Those users get no arrows on hover, and if dots are also gated behind hover (see below) they get no visible carousel affordance at all. Fix: gate visual arrow hiding on `(hover: none)` alone, or show arrows whenever `any-hover: hover` matches, and add a media-emulation test for the coarse+hover combination.

MAJOR verification-and-rollback — Plan §"Test Strategy" (Playwright desktop) / §"Assumptions" — the plan never states whether the dots are visible at rest on fine pointer; the desktop acceptance says "Fine-pointer controls hidden at rest" while the touch row treats dots as the always-available affordance. Built one way, desktop users get no position indicator until hover; built the other, the acceptance test contradicts the implementation and gets loosened during the run. Fix: state explicitly that dots are always visible (rest and hover) on all pointer types and that only arrows are hover/focus-gated, then assert dot opacity at rest in the desktop test.

MAJOR verification-and-rollback — Plan §"Risk-Matched Verification" row "Threefold dashboard image traffic" — the acceptance threshold is DOM `<img>` mount counting, with network observation only "when cache permits". Mount counts cannot detect a regression that adds `<link rel=preload>`, `new Image()` prefetch, or a hidden decode warm-up, so the stated risk would not fail the test if the change were wrong. Fix: make the request-count assertion mandatory via `page.route`/`page.on('request')` filtered to `/api/mockups/image` with cache disabled for that spec, and treat the DOM check as secondary.

MINOR product-and-scope — Plan §"Plan" step 3 (122px details area, title/date row, clipped description) — fixed-height details with no stated truncation rule for the title; a long project name will either wrap into the date row or overflow the 122px box, and the geometry test (±1px on fixed heights) would still pass. Fix: specify single-line title truncation plus the description line-clamp count, and add a long-name/empty-description fixture to both the render test and the Chrome evidence.

MINOR product-and-scope — Plan §"Plan" step 4 / §"Test Strategy" — no slide transition or `prefers-reduced-motion` handling is specified, so the implementer will invent an animation (or none) unreviewed; an animated slide on a grid of cards is exactly the kind of motion the plan elsewhere rejects as competing with scanning. MINOR runtime-and-change-impact — Plan §"Failure And Recovery" / §"Architecture Improvement Opportunities" (retain visited slides) — the plan never says whether the visited-slide set and per-slide image-failure map reset when `mockupPreviews` changes identity (the same event that resets the index to A). Stale entries keyed by position would mount a previous project version's URL or suppress a retry on a now-valid image. Fix: state that visited and failed sets are keyed by preview URL/label and cleared with the same signature change that resets the index.

MINOR security-and-data-integrity — Plan §"Failure And Recovery" (gesture-scoped navigation suppression) — the suppression flag is cleared by "click or next touchstart", but a qualified swipe whose `touchend` lands outside the link synthesizes no click, leaving the flag set until an unrelated later interaction; combined with `router.refresh()` re-mounting the thumbnail, the flag's lifetime relative to component remount is unspecified. Worst case is a card whose first real tap is swallowed. Fix: scope the flag to the gesture by resetting it on `touchcancel` and on unmount as well, and add a Playwright case where the swipe ends outside the card bounds followed immediately by a tap.
